# Background Computer Use

Computer use for macOS agents that never takes your focus. Agents work in your real, logged-in apps, in windows on a private virtual display you don't see, while you keep using your Mac. A menu bar app shows what each agent is doing, with a live view of each agent's display that you can click to expand.

No app is modified and nothing is app-specific. It only uses what macOS provides for every app: a virtual display (`CGVirtualDisplay`), Accessibility, per-process input events (SkyLight), and direct window capture.

## Install

Download the app from **https://apps.moulik.dev/background-computer-use/**, open the DMG and drag it to Applications. Open it and follow the setup window. It asks for Accessibility and Screen Recording, reopens itself once, and then adds the MCP server and the skill to Claude Code and Codex.

It updates itself. Updates download in the background and install when you quit the app or when no agent is working, so an agent is never cut off mid-task. "Check for Updates…" is in the ⋯ menu.

### Build from source

```bash
scripts/build-app.sh --install
```

This builds `Background Computer Use.app`, signs it with your Developer ID (or ad hoc), copies it to /Applications and starts it. Permissions carry over between builds only while the Developer ID team stays the same; an ad hoc build asks for them again.

Releases: push a tag `vX.Y.Z` on main. The release workflow (from [app-hosting](https://github.com/Moulik-Budhiraja/app-hosting), configured by `apps.json`) builds with `scripts/build-app.sh`, signs with the Developer ID, notarizes and publishes to the update feed.

## Connect an agent

The setup window does this for you. To do it by hand, or for another agent:

Claude Code:

```bash
claude mcp add --scope user background-computer-use -- "/Applications/Background Computer Use.app/Contents/MacOS/bcu" mcp
```

Codex (`~/.codex/config.toml`):

```toml
[mcp_servers.background-computer-use]
command = "/Applications/Background Computer Use.app/Contents/MacOS/bcu"
args = ["mcp"]
```

Then install the skill for both:

```bash
"/Applications/Background Computer Use.app/Contents/MacOS/bcu" install-skill
```

The MCP server's instructions tell the agent how to work: open a window of the app (or the default browser) on its display, read it with `get_window_state`, act on numbered elements, release windows at the end, and hand off to you when it needs you. The skill ([skills/background-computer-use/SKILL.md](skills/background-computer-use/SKILL.md)) goes further: how to read the tree, which action to prefer, when to batch, which of your accounts it may use, and which steps to confirm with you first. An agent uses the accounts your request involves, plus the ones the task expects along the way, such as your email for a sign-in code. It asks before reaching into a different system than the one the task is about (fixing a networking bug in an app doesn't let it open your router settings), unless you told it to do whatever it takes. It creates accounts only when you ask, and then accepts the terms without asking. Anything other people will see (sending, posting, submitting a form), deleting for good and paying need your yes unless your request names that step, even when you said to do whatever it takes. The agent works out every approval up front and asks for them in one message. It never types or reads your passwords. It fills them from your browser's or password manager's autofill, and `get_window_state` hides password fields. Every word an agent sees, from the server instructions to each tool's description to the skill, is in [docs/agent-context.md](docs/agent-context.md), generated by `bcu docs`.

After the first read of a window, `get_window_state` lists only what changed, and an element keeps its number for as long as it exists. Right after an action it waits up to 5 s for the window to settle. `batch` runs a list of actions in one call (say, click the address bar, type a URL, press Return), stops at the first failure, and returns the changes at the end, so the agent makes fewer round trips to the model.

For debugging: `bcu call <tool> '{json}'`, `bcu status`, `bcu tools`, `bcu docs`. The test tools (`admin_*`, which can type into and close any app's windows) answer only `bcu call`, and only when the app was started with `open --env BCU_ADMIN_TOOLS=1 "/Applications/Background Computer Use.app"`; they aren't listed and `bcu mcp` refuses them.

## Use it from another app

Another app can run the engine itself and show its agents' screens in its own UI: `bcu serve` runs the engine without the menu bar app, `bcu mcp --host <id>` tags an agent's session as that app's, and a socket protocol carries session state, live preview frames, take-over input and handoffs. Only one engine runs on a Mac, whichever app started it, and this app takes over from another app's engine once its agents are idle. See [docs/embedding.md](docs/embedding.md), and [clients/typescript](clients/typescript) for a client for Node and Electron.

## How it stays out of your way

- **Its own display.** Each agent session (each `bcu mcp` connection) gets a 1600×1000 Retina virtual display (3200×2000 pixels, so the live preview stays sharp; the preview captures the whole display in one call, about 18 ms a frame, with no screen-sharing indicator) touches your screens at one corner. A second agent's display touches the first one's far corner, and so on, so sessions never share windows, pause or take-over. Subagents count as agents too: Claude Code runs them over their parent's connection, so `bcu mcp` tells their calls apart by the tool-use ID each call carries, which Claude Code writes to the calling subagent's transcript first (Codex starts a separate `bcu mcp` per subagent and tags calls with a thread ID). A subagent can still use a window its parent handed it. At most 4 agent displays exist at once; an agent that needs one past that waits (up to 45 s) for one to go away, and while it waits, displays with no windows go after 5 s. A display is made when its agent opens its first window. After 60 s with no windows and no calls (at once when its agent's connection goes away) it's set aside rather than removed, and the next agent takes it over; one that no agent has needed for 5 minutes is removed, as are all spares when the Mac goes to sleep. The displays stand in a staircase, and one is only ever removed from its far end: macOS leaves no gap, so taking one out from under a display in use moved that display and threw its windows onto your screen on the way (measured on 0.1.18: an agent's window on the main display for half a second when three idle displays before its own were removed). A display with one in use after it holds its place until that one is done. That's because every display added or removed makes macOS rearrange them all: the whole screen stalls for a few hundred ms, and macOS puts your windows back where they were the last time the displays were arranged that way (a browser window you've since made small goes back to filling the screen). Kept displays make that once per stretch of agent work instead of once per agent, and each time the app notes where your windows are first and puts back any that macOS moves. A display is never let go while a window is still on it, since macOS would move the window onto your screen: what's left is closed first, and if it won't close the display stays. An event tap keeps your cursor off it, and a watcher thread checks the cursor every 4–16 ms and pulls it back from anything that got past the tap (the tap not installed yet or disabled by macOS, displays being rearranged, another app warping the cursor).
- **No capture indicator.** macOS counts how often an app reads other apps' pixels and shows its purple screen-capture pill once that passes about 10–15 reads close together (SkyLight window captures, `CGDisplayCreateImage` and the `CGWindowList` image calls all count, at any size, even on the agent display). One-shot ScreenCaptureKit screenshots don't count, so agent screenshots and the live preview use them. They draw window rims and the menu bar a little differently from the screen, so the still copy of your window during a key swap uses a counted capture, rationed well below macOS's limit.
- **Background input.** Clicks and keys are posted to one process through SkyLight, stamped with the target window. Accessibility actions (`AXPress`, value writes) are preferred because they need no keyboard focus.
- **Shared apps.** You and the agent can use the same app at once (say, both in Helium). Element clicks and value writes go through accessibility and never touch your window. Keystrokes and pixel clicks go to an app's key window, so the agent makes its window key inside the app for a moment and hands key straight back to yours, under a still copy of your window and the menu bar. What you type into that app and your clicks on it during that moment (0.3–0.45 s measured in Helium) are held and replayed in order; nothing else is held, and nothing is held for the copy. While you're typing, the copy leaves out what's inside your window and covers only what typing doesn't change (its title bar and toolbars, its shadow, the menu bar), so your text keeps appearing as you type it; a full copy turns into that the moment you press a key or a mouse button. Such a step waits for you first. Your typing always goes first: the step doesn't start until 2 s after your last key, however long you type (shorter gaps are part of typing: a key every 600 ms at 20 words a minute, a second to find a word), and if it's about to start when you type again, it backs off and waits again. A step that has waited 30 s is refused with nothing done, so that no tool call hangs for as long as you write an email; the agent retries, or does something that needs no key focus meanwhile. That's **Safe typing** in Settings, on unless you turn it off (`BCU_SAFE_TYPING=0` at launch for an engine without the app): off, your typing is waited for like a click, 3 s at most, so an agent in the app you're writing in is faster and your keys can arrive up to half a second late (numbers under the table in [Status](#status)). For the rest, a step waits 700 ms after your last click (or the double-click interval, if longer), 200 ms after a scroll and its momentum end, and while you hold a key or mouse button or have a menu open. After 2 s of that any 150 ms gap in your input will do, and after 3 s it runs anyway, unless you're mid something that breaks when focus moves (a menu open, a mouse button held for a drag or selection, a key held): then the step fails rather than interrupt it, and the agent retries. Opening a window and loading a URL follow the same rule: in the app you're in they wait like this, and in any other app they wait while you hold a button or key or have a menu open anywhere. In the app you're in, your input is held only from the moment the new window shows (it takes key) until key is back on yours: 0.25–0.4 s on a 4-core test Mac, about as long as a Chromium browser stays busy drawing a new window anyway. Waits for clicks and scrolling are capped at a fifth of the agent's working time, so even if you never stop, a task slows down by about that much; waits for typing aren't capped, so an agent working in the app you're writing in gets its key steps done in your pauses. In a batch, back-to-back steps like this wait once and run under one copy, unless you type under it. An agent can pass `priority: "now"` for a step that can't wait (a toast about to close): it skips these waits, except the one for your typing. Apps you aren't in don't wait: a key swap in an app that isn't frontmost doesn't change anything on screen. In those apps the agent's window keeps key focus after its step instead of giving it up, because a web page takes losing key as leaving the field (dropdowns close, comboboxes clear), and the next step would find the form reset. When you switch to that app (a click on one of its windows, `cmd+Tab`, the Dock), key goes to your window, the one in front on your screen, within 10–50 ms, and what you type meanwhile is held and then replayed into it. Two agents in the same app take turns: a step that needs key waits while another agent's window has it and that agent did something there in the last 6 s (20 s at most), and so does opening a window in that app. Before every key it sends, the agent checks its window still has key focus; if you switch to that app partway (a click, `cmd+Tab`), it stops and reports how far it got, and the keys you type there wait until your window has key again. Your clicks on that app's windows wait for the swap too. Keystroke typing goes in swaps of at most 16 characters and 400 ms, and nothing holds your input for more than 2 s: after that the guard lets it go, and drops keys rather than type them into an agent's window if your window still doesn't have key.
- **Loading a URL.** `navigate` tells a Chromium browser to load a URL in the agent's window by Apple event, with no keystrokes, in the window the browser knows by its own id. Which of the browser's windows that is gets proven, not matched by frame: displays come back at the same place and windows are laid out the same way on them, so a window left from an earlier task sits at exactly the agent's frame (on 0.1.18 the load is then refused, "more than one window with bounds", or goes into the other window). So before its first load the agent's window is moved 3 points through accessibility and back, and the id is the one whose window the browser reports at the new place; before every later load the browser's window with that id has to be where the agent's is. It returns when the browser says the tab has loaded, or after 3 s if it's still loading: until the new page takes over, the window's accessibility tree is the old page's, loaded and still, and a read just then would take it for the new one.
- **Web content.** Chromium and Electron build their full accessibility tree (with press actions on links and buttons) only when an assistive app asks. The agent sets `AXEnhancedUserInterface`, the standard attribute VoiceOver uses, once per app. Popups the agent's window opens, like address-bar suggestions, are listed with its elements so the agent can press them.
- **Front gate.** An app can bring itself to the front whenever it likes: Chromium does each time it shows a window or loads a URL it's handed, Finder and Electron apps too, and no other process can stop the call. Putting your app back afterwards is too late: for those 10–60 ms the menu bar shows the other app's menus, your window is drawn inactive with a lighter shadow, hover effects under your pointer end, and the app's own windows on your screen can stay on top of yours. So the app doesn't undo it, it has macOS refuse it. LaunchServices keeps a list of the apps allowed to make themselves frontmost (what kiosk and exam modes use), and WindowServer turns down anyone else ("Denying Helium the right to be in front because it is not in the list of permittedFrontASNs") with nothing changing on screen. While agents have windows in apps you aren't in, the list holds every running app but those. The list would keep you out of them too, so the gate opens the moment you do anything that could be a switch, before the event goes on: any mouse button (for 1 s: a link you click can take a moment to bring the browser forward), `cmd+Tab` for as long as you hold command, Return, a function key or a key with a modifier (1.5 s). Typing, scrolling and moving the pointer leave it shut. A helper process clears the list if the app dies (measured: within 0.3 s) or stops answering (3 s), a new launch clears whatever a crash left, and a list some other app keeps is never touched.
- **Focus guard.** For the moments the gate is open, and on a macOS without it: the front app is sampled every millisecond while agents have windows. If an agent's app makes itself frontmost, your app is put back, given its key window again once it's active (in front with no key window it's drawn inactive though your typing reaches it) and raised over any window the other app left on top of it, and keys you typed in between are held and replayed. Each tool result reports a change once, in the call it happened in or the next one, and only to the agents working in that app.
- **Taking over.** Click the expanded view's preview (or the hand button) and confirm, and the preview works like a VNC window: your clicks, drags, scrolls and keys over it go to the agent's window under the pointer, posted the same per-process way the agent's input is. A click is sent when you let go of the button and a drag once the pointer moves. Dragging a title bar (or empty tab strip) moves the window, which can hang off the left, right and bottom edges like on any Mac, and dragging an edge resizes it; both are done through accessibility, because the window server would run them against your real cursor, and the preview draws the window where it's going because accessibility moves show up about 100 ms late. A right click opens the element's context menu through accessibility (AppKit apps close a menu opened by a synthetic click as soon as they're no longer active), and clicks on menu items press them the same way. The pointer takes the shape the app under it would show: resize arrows at window edges, a hand over links, an I-beam over text. Any app that brings itself forward is sent back. The dimmed backdrop goes away, so outside the preview your mouse and keyboard work as usual. The agent's actions are refused until you press Done. `cmd+Q` isn't passed on, because it would quit the whole app, your own windows included.
- **Several agents.** The popover shows one live preview per agent display, labeled with the agent (Claude Code, Codex), and grows to fit: two side by side, a 2×2 grid for three or four, three across for five or six. Click a preview to expand that display. Pause and stop in the popover act on every agent; the expanded view's act on that one.
- **History.** Every agent display is recorded while it exists, so you can look back at what an agent did after the fact. Sessions of another app that runs agents through the engine (see [Use it from another app](#use-it-from-another-app)) aren't in it: that app chooses whether they're recorded, and keeps its recordings in its own folder. The clock button in the popover (or in an expanded view, for that agent) opens a timeline laid out like Coast's: the frame on top, and under it a track of frames from oldest to newest, grouped by app with its icon and labeled where each agent's display started. It opens on the newest frame. Swipe with two fingers, scroll or drag the track to move through time, click it to jump, ← → step a frame, ⌥← ⌥→ or the arrows on the frame's edges jump to the previous or next app, ⌘← ⌘→ go to the start and end, ⌘+ ⌘− zoom the track, pinch (or double-click) zooms into the frame, and Esc closes. The header shows the app, the agent, the time and the agent's last action, and the frame shows the agent's pointer and its clicks. Text in a frame can be selected and copied, and the text button highlights it. Frames are 2400×1500 and kept only when the display changed (a blinking caret doesn't count). The recorder captures the display window by window, at most every 4 s and only once nothing else in the app has captured for 4 s, because captures every 2 s or so make macOS turn on its purple screen-sharing indicator. Each agent screenshot from `get_window_state` or `screenshot` is drawn over the last frame as a new one, and while the live preview is open its frames are recorded twice a second, so neither costs another capture. Frames go to disk as JPEGs first, so a recording can be watched while it's made and survives a crash, and every minute they're packed into an HEVC video. Recordings stay on your Mac in `~/Library/Application Support/BackgroundComputerUse/recordings` and are deleted 7 days after they end, or sooner once they take more than the space set in Settings (300 MB by default; the oldest go first). `BackgroundComputerUse --history-selftest <dir>` records made-up frames into `<dir>` through the same code, reads them back and renders the viewer to PNGs. `--history-render <dir>` renders the viewer from your own recordings, at the start and end of each app stretch, and the Settings window.
- **Sound.** An app whose windows are all on agent displays plays nothing on your speakers. A Core Audio process tap mutes it (helper processes included, matched by bundle ID) and, while it is playing, records it to `$TMPDIR/bcu-audio/<agent>-<session>.aac`, which `status` tells the agent about. The file is readable while it is written and deleted when the session's display is removed. Apps you also have windows in, minimized or hidden ones included, play normally. macOS shows its purple recording dot next to Control Center while the recorder runs, which is while an agent-only app holds its audio output open; muting alone shows nothing.
- **Leftovers.** The app's windows are tracked on disk, so a crash or restart closes the agent's windows instead of leaving them behind. An agent that goes away without releasing its windows (its connection closes) has them closed 30 s later (5 s when another agent is waiting for a display), and its display freed at once if it had none. An agent whose `bcu mcp` was restarted comes back under a new session id: its first call on one of its windows makes it the old session again, with the same display and windows, instead of failing with "isn't one of yours" while the old session keeps them. A window counts as gone only when the window server says so: an app that isn't answering accessibility (busy, or showing a dialog) still has its windows, and forgetting one would leave it open with nobody to close it. A page that asks "Leave site?" when an agent closes its own window gets Leave, the moment the dialog shows (it comes up on your screen); any other dialog an agent's step raises, at any window level, is moved over the agent's window where the agent finds it listed.

## Status

Early, but the core works. Measured on macOS 26.6 against real apps (Helium, TextEdit):

- **Focus test:** a script typed 627 characters into TextEdit on the user's screen while the agent opened Helium windows, navigated with keystrokes, used `cmd+L` and scrolled. All 627 characters landed in TextEdit, twice. Keys typed during Helium's self-activation were held and replayed.
- **Shared Helium** (macOS 15.7): with the user's Helium window in front and a script typing 102 characters into it, the agent typed a URL and Return into its own Helium window's address bar, typed into a field, pressed Tab and typed two lines into a text area. All 102 characters landed in the user's window in order, and it ended key. Filming the screen showed nothing change for the agent's steps. Its text went in through accessibility. For Return and Tab its window did take key focus, and underneath the user's window was drawn inactive and the menu bar dimmed for 100–200 ms each time, but a still copy of both covered that. Before, each `type_text`, `press_key` or pixel click showed the user's window inactive and the whole menu bar dimmed for 130–470 ms.
- **Shared TextEdit** (macOS 15.7): the same test in TextEdit, with the agent typing, pressing Return, `cmd+A` and an arrow key in its own document. Both texts were exact, and nothing changed on screen; before, the user's window, its shadow and the menu bar changed for 85–370 ms per step.
- **Waiting for the user** (macOS 15.7, a script typing, clicking, scrolling and opening menus in the user's TextEdit or Helium window while the agent pressed keys and clicked in its own window of the same app): no swap started while a key or button was held, and none during a menu the user held open for 2.5 s; the step ran after it closed. Waits were 0.1–0.9 s around clicks and 0.3–1.2 s around trackpad scrolls. Typing is waited out however long it lasts: with a script typing nonstop into the user's browser window (8 keys a second for over two minutes), no step of the agent's that takes key started, each try to open a window was refused after 30 s, and all 1,104 keys arrived within 23 ms. With the script typing in bursts instead (the table below), the lab's 20-call browser task took 65–104 s, against 23 s on 0.1.18, where steps cut in. Every key the user typed landed in their window, in order.
- **Agent tools:** accessibility values, element presses, keystroke typing, `cmd+A` and other menu shortcuts, menu items, scroll, save sheets and logged-in web pages all work in the background.
- **Invisibility lab** (macOS 15.7, 4-core VM; `Tools/Lab`, see [Testing](#testing)): a simulated user types nonstop (one key every 110 ms) into a window of their own with the pointer resting on a hover target, while scripted agents open windows, load pages, press, type, press Return, scroll and click. Known gaps:
- **Same app, typing that starts mid-step.** An agent's step that takes key focus in the app you're in never starts while you type, but one already under way when you start again has to finish first: taking key and giving it back takes 0.2–0.45 s, a new window up to 0.6 s (on a 4-core VM), and the first one to four keys you type wait for it. How often depends on how you type: a step that has been waiting goes 2 s into your pause, so it's the pauses of two to two and a half seconds that get caught (measured: 1–2 keys in 300–550 with one agent, 12 in 780 with three, against a script that paused that long often). A step that hasn't sent anything yet gives key straight back, and your key waits 0.1–0.25 s instead. Each such step still gives your page a blur and a focus event and restarts a hover effect under your pointer; the menu bar, your title bar and your shadow stay as they were under the copy. A key reaches a window only while it's its app's key window, or, in Chromium, its main window whatever window the event names (measured: a Return stamped for the agent's window went to the user's page when theirs was main), so there's no sending it past your window.
- **An agent in the app you're writing in is slow.** Its `press_key`, Return and Tab, pixel clicks, new windows and URL loads wait for your pauses, and fail after 30 s without one (clicks on elements, `set_value` and typed text go through accessibility and don't wait). Against nonstop typing it gets none of those done. Turning Safe typing off in Settings trades that back: the agent's steps go in between your keystrokes after 3 s at most.
- **Just after you click.** The front gate is open for 1 s after any click and 1.5 s after Return or a shortcut. An agent's app that brings itself forward in that time gets there, and is put back 20–80 ms later as before.
- **Adding a display.** The first agent after a quiet 5 minutes adds a display (`BCU_SPARE_DISPLAY_S` at launch sets how long an unused one is kept; 0 for never). macOS stalls as it does: keys typed meanwhile arrive late, by under 10 ms for one display on the test VM but by 0.3–0.4 s when four agents start together and add four (0.7 s on 0.1.18). Waiting for a pause in typing before adding one, and adding them one at a time, were both tried and measured no better: four displays take longer to add than most pauses last, and the fourth stalls as long by itself. It also moves any window of yours that has changed place since the last time an agent display existed back to where it was then; the app puts it back where you have it, which takes up to 1.2 s (the window's app is busy with the new display too).
- **First window of an app you already use.** Chromium browsers (Helium, Chrome, Brave, Edge…) are asked to build the new window at its place on the agent display (the Apple event AppleScript's `make new window with properties {bounds:…}` sends, sent by the app itself: running `osascript` for it took 0.2–0.9 s, and over 6 s on a busy Mac, where windows then failed to open). The browser puts the window where it would have opened and moves it in the same breath, so normally it never appears on your screen, whatever you have open. On a Mac too busy for that (seen in 1 of 4 runs on a 4-core VM with no GPU, with four agents starting at once, four displays being added and the screen being filmed) it shows there first, behind the window you're in, for 0.3–0.5 s. Nothing opens while displays are being added or for 0.7 s after: an app sent to a display it hasn't heard of yet puts the window on your main display (measured: for 1.5 s); macOS asks once per browser whether Background Computer Use may control it: setup asks for your default browser, any other browser is asked the first time an agent opens one of its windows, and until you allow it that window opens the old way. Other apps open new windows next to an agent's existing window of the app (this session's or another's) and never appear on your screen; when no agent has a window of that app yet, the first one shows on your screen for about 100–550 ms before it is moved. macOS gives other processes no way to place another app's window: it won't let them move it, change its alpha or move it to another Space, accessibility can't see a new window until it's shown, and apps place new windows from their own last window, not from the display or the pointer. Assigning the app to the agent display's Space (the Dock's "Assign To") would open new windows there but moves your windows of the app too. Since the app no longer comes to the front to show it, that first window opens behind the window you're in (measured: Finder's for 70–270 ms, TextEdit's for 15–110 ms), so it shows only where your window doesn't cover it. If your pointer is where a window opens, hover effects in your window (a video preview, say) end, and they come back once the window is gone. Adding an agent display also makes macOS send a 2 ms mouse exit and re-entry to the window under your pointer.
- **Key focus in an app you're using.** Keys that aren't text (`press_key`, Return, Tab), pixel clicks, and fields that ignore accessibility writes still give the agent's window key focus in that app for 100–300 ms. The screen doesn't show it, but the app sees it: a web page in your window gets blur and focus events, and a popup open in your window (address-bar suggestions, a menu) closes. Your input is held for that moment and each such step takes about 200 ms longer. Steps wait for you to stop typing, and up to 3 s for a pause in clicking or scrolling; with a menu open in that app the step fails instead of closing it.
- **Capture indicator on macOS 15.** On macOS 15 a single counted capture shows a small capture dot next to Control Center for about 11 s, so the still copy shows it there. Whether ScreenCaptureKit screenshots do too on macOS 15 hasn't been measured.
- **A macOS without the permitted-front list.** The front gate uses LaunchServices calls that aren't public (checked on macOS 15.7). Where they're missing, or while another app keeps such a list of its own, an agent's app that brings itself forward is put back after the fact (20–80 ms, the menu bar can flicker).
- **Audio before the first sound.** An app gets a Core Audio process only when it first plays something, so the first few milliseconds of an agent-only app's first sound can reach the speakers before the tap is in place.
- `SLSProcessAssignToSpace` would open windows on the agent display with zero frames, but it moves every window of the app, yours included, so it's disabled (placement `space-unsafe`).

## Testing

`Tools/Lab` measures, from outside the app, what a user would see and feel while agents work. `Tools/Lab/build.sh` builds `build/lab/lab` (the observer and a simulated user that types and moves the pointer through the real input stream) and `BCU Fixture.app` (an app standing in for the one the user is in, which writes down every key with how long it took to arrive, every time it lost or gained key or active state, and every hover that ended). Then, with the engine running:

```bash
python3 Tools/Lab/run.py scenario --agents 2 --kinds helium,finder --out /tmp/lab-run
python3 Tools/Lab/run.py scenario --agents 1 --kinds helium --user helium --out /tmp/lab-shared   # the user in the same browser
python3 Tools/Lab/run.py scenario --agents 3 --kinds helium --user helium --burst 22 --pause 1200 --spread 0.9 --seed 21 --out /tmp/lab-bursts
```

The simulated user types nonstop unless `--burst` is given: then in runs of about that many keys with a pause after each (`--pause` ms, spread log-normally with `--spread`), and with `--seed` in the same rhythm every run, so two builds can be measured against the same typing.

The front gate rests on LaunchServices calls that aren't public, so a macOS version it hasn't run on gets checked first: `python3 Tools/Lab/gate_check.py probe /tmp/gate` (macOS alone: is the list honored, and does clearing it let every app forward again) and, with this build's engine running, `python3 Tools/Lab/gate_check.py engine /tmp/gate` (the gate arms, a click and cmd+Tab still get you into the agent's app, the helper clears the list when the engine is killed). Both pass on macOS 15.7.

Each run prints one line per thing the user could notice (front app, menu bar, title bar, shadow, hover, typing, windows, cursor, displays) and saves the raw records, the frames that differed most, and the engine's log for the run. Run it on a Mac nobody is using: the simulated user types into whatever of its own is in front. The shell it runs from needs Accessibility and Screen Recording.

WindowServer logs every change of front app and every one it refuses, which tells an app that got to the front by itself from one that was put there:

```bash
log stream --info --debug --predicate 'process == "WindowServer" AND subsystem == "com.apple.SkyLight" AND category == "processes"'
```
